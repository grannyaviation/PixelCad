# Centring — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the two centring semantics that are still missing — drag-time "centre inside an area" in both eeschema editors, and align-centre commands in the symbol editor, which is the only one of KiCad's four editors without them.

**Architecture:** Phase A extends the existing guide engine: `SetContainers()` is already implemented and tested but called only by pcbnew, so eeschema just needs to feed it (symbol body outline in the symbol editor, drawing sheet page in the schematic). Phase A also replaces the engine's crosshair `CenterMarks` with ordinary guide lines, which fixes a known limitation and deletes code. Phase B adds a symbol-editor align tool: the generic geometry is extracted from the existing `SCH_ALIGN_TOOL` and shared, while each editor keeps its own selection, move and cleanup, because the schematic's cleanup is wire/junction work that has no meaning in a symbol.

**Tech Stack:** C++20, KiCad 10.99 master, Boost.Test (`qa_common`, `qa_eeschema`), CMake + Ninja under `nix develop`.

## Research findings this plan is built on

Verified in the tree, not assumed:

- **`SetContainers()` already works.** `ALIGNMENT_GUIDE_ENGINE` generates `KIND_CONTAINER` candidates and three tests cover them (`test_alignment_guide_engine.cpp:288,311,357`). The only caller is `pcb_grid_helper.cpp:668-672`, which feeds `board->GetBoardEdgesBoundingBox()`. Nothing in eeschema calls it, which is the entire reason there is no centre-in-area guide there.
- **`CenterMarks` is `std::vector<VECTOR2I>` and carries no axis**, so a snap that centres on one axis only still draws a full crosshair (`alignment_guide_geom.cpp:119-123`). Every consumer is listed in Task A1; there are five.
- **`SCH_ALIGN_TOOL : public SCH_TOOL_BASE<SCH_EDIT_FRAME>`** (`sch_align_tool.h:32`) — bound to the schematic frame, so it cannot simply be registered in the symbol editor. It is registered at `sch_edit_frame.cpp:712`; the symbol editor's `RegisterTool` block (`symbol_edit_frame.cpp:477-493`) has no align tool at all.
- **eeschema has no distribute commands.** `sch_align_tool.h` declares only `AlignTop/Bottom/Left/Right/CenterX/CenterY`. Phase B therefore ports *align* only. Distribute would be new functionality in two editors and is explicitly out of scope.
- **Of the tool's five helpers, two are generic and three are not.** `selectTarget()` is pure geometry plus the cursor. `GetSelections()` filters on `SCH_COLLECTOR::MovableItems`. `moveItem()` commits with `aCommit.Modify( aItem, m_frame->GetScreen(), RECURSE_MODE::RECURSE )`. `doAlignCleanup()` calls `SCH_LINE_WIRE_BUS_TOOL::TrimOverLappingWires`, `AddJunctionsIfNeeded` and `m_frame->Schematic().CleanUp()` — none of which exists in a symbol.
- **Geometry APIs confirmed:** `PAGE_INFO::GetSizeIU( double )` (`include/page_info.h:173`), `LIB_SYMBOL::GetBodyBoundingBox( int aUnit, int aBodyStyle, bool aIncludePins, bool aIncludePrivateItems )` (`lib_symbol.h:331`).

## Why Phase B duplicates rather than templates

Templating `SCH_ALIGN_TOOL` on the frame type would mean making `doAlignCleanup`, `moveItem` and `GetSelections` all conditional — three of five helpers — inside code the schematic editor depends on for a shipping feature. Task B1 instead extracts only what is genuinely shared (the target-selection rule and the six align arithmetic operations) into a frame-agnostic helper, leaving both tools owning their own I/O. That is a pure extraction: the schematic's behaviour must not change, and Task B1 proves it by running the existing suites before touching the symbol editor.

```cpp
    }
```

```cpp
    // Containers: the area the moving item can be centred inside.  Mirrors the board outline
    // pcbnew feeds (pcb_grid_helper.cpp).  Both are computed once per drag, like the sweep above.
    if( symbolEditor )
    {
        // The body outline the user is drawing around the pins.  Pins excluded: a container is
        // the drawn area, and pins stick out of it by their length in every direction, which
        // would centre a graphic against something nobody sees as the body's edge.  Private
        // items excluded for the same reason.
        if( LIB_SYMBOL* symbol = symbolEditor->GetCurSymbol() )
        {
            const BOX2I body = symbol->GetBodyBoundingBox( symbolEditor->GetUnit(),
                                                           symbolEditor->GetBodyStyle(), false,
                                                           false );

            // A symbol with no graphics yet yields a default-constructed box, which the engine
            // would take at face value as a container at the origin.
            if( body.IsValid() )
                engine.SetContainers( { body } );
        }
    }
    else if( SCH_SCREEN* screen = static_cast<SCH_SCREEN*>( m_toolMgr->GetModel() ) )
    {
        // The drawing sheet page.  The origin is (0, 0) by KiCad convention and the page grows
        // right and down, so the rectangle is the page size at the origin.
        const VECTOR2D size = screen->GetPageSettings().GetSizeIU( schIUScale.IU_PER_MILS );

        if( size.x > 0 && size.y > 0 )
            engine.SetContainers( { BOX2I( VECTOR2I( 0, 0 ), VECTOR2I( KiROUND( size ) ) ) } );
    }
```

Create `common/tool/align_geom.h` with the standard KiCad GPL header block (copy the one from `include/tool/alignment_guide_engine.h`), then:

```cpp
#pragma once

#include <cstddef>
#include <optional>
#include <vector>

#include <math/box2.h>
#include <math/vector2d.h>

/**
 * The frame-agnostic half of align-to-edge.
 *
 * Both the schematic and the symbol editor align a selection the same way -- pick a target,
 * then move every box onto its edge or centre on one axis.  What differs is everything around
 * it: which items are selectable, how a move is committed, and what has to be cleaned up
 * afterwards (the schematic re-trims wires and re-adds junctions; a symbol has neither).  So the
 * arithmetic lives here and the I/O stays in the tools.
 *
 * Pure geometry: no tool, frame or wx dependency, and unit-testable headless.
 */
namespace ALIGN_GEOM
{

enum class MODE
{
    TOP,
    BOTTOM,
    LEFT,
    RIGHT,
    CENTER_X,
    CENTER_Y
};

/**
 * The box the others should line up against: whichever one the cursor is inside, else the
 * first.
 *
 * "Else the first" is not arbitrary -- callers sort by the edge being aligned, so the first box
 * is the extreme one on that axis, which is the sensible default target.
 *
 * @return index into aBoxes, or nullopt when aBoxes is empty
 */
std::optional<size_t> SelectTargetIndex( const std::vector<BOX2I>& aBoxes,
```

- [ ] **Step 4: Write the implementation**

Create `common/tool/align_geom.cpp` with the GPL header, then:

```cpp
#include <tool/align_geom.h>

namespace ALIGN_GEOM
{

std::optional<size_t> SelectTargetIndex( const std::vector<BOX2I>& aBoxes,
                                         const VECTOR2I&           aCursor )
{
    if( aBoxes.empty() )
        return std::nullopt;

    for( size_t i = 0; i < aBoxes.size(); ++i )
    {
        if( aBoxes[i].Contains( aCursor ) )
            return i;
    }

    return 0;
}


std::vector<VECTOR2I> Deltas( const std::vector<BOX2I>& aBoxes, MODE aMode, const BOX2I& aTarget )
{
    std::vector<VECTOR2I> deltas;

    const BOX2I& target = aTarget;

    deltas.reserve( aBoxes.size() );

    for( const BOX2I& box : aBoxes )
    {
        switch( aMode )
        {
        case MODE::TOP:
            deltas.emplace_back( 0, target.GetTop() - box.GetTop() );
            break;

        case MODE::BOTTOM:
            deltas.emplace_back( 0, target.GetBottom() - box.GetBottom() );
            break;

        case MODE::LEFT:
            deltas.emplace_back( target.GetLeft() - box.GetLeft(), 0 );
            break;

        case MODE::RIGHT:
            deltas.emplace_back( target.GetRight() - box.GetRight(), 0 );
            break;

        case MODE::CENTER_X:
            deltas.emplace_back( target.Centre().x - box.Centre().x, 0 );
            break;

        case MODE::CENTER_Y:
            deltas.emplace_back( 0, target.Centre().y - box.Centre().y );
            break;
        }
    }

    return deltas;
}

} // namespace ALIGN_GEOM
```

The existing `selectTarget()` implements this precedence, which `applyAlign` must reproduce
exactly: **when any item is locked the target comes from the locked set alone** — the
cursor-contained one, else `aLocked.front()` — and otherwise from `aItems`, cursor-contained
else `aItems.front()`. That is what makes locking an item a way of nominating it as the thing
everything else lines up against.

```cpp
void SCH_ALIGN_TOOL::applyAlign( std::vector<ITEM_BOX>& aItems,
                                 const std::vector<ITEM_BOX>& aLocked, ALIGN_GEOM::MODE aMode,
                                 SCH_COMMIT& aCommit )
{
    // Locked items are never moved, but they are the *preferred* target: aligning to something
    // that cannot move is the whole reason a user locks it first.  So the target is picked from
    // the locked set when there is one, and only the unlocked items receive a delta.
    const std::vector<ITEM_BOX>& targetPool = aLocked.empty() ? aItems : aLocked;

    std::vector<BOX2I> targetBoxes;

    for( const ITEM_BOX& item : targetPool )
        targetBoxes.push_back( item.second );

    std::optional<size_t> target =
            ALIGN_GEOM::SelectTargetIndex( targetBoxes, getViewControls()->GetCursorPosition() );

    if( !target )
        return;

    std::vector<BOX2I> boxes;

    for( const ITEM_BOX& item : aItems )
        boxes.push_back( item.second );

    const std::vector<VECTOR2I> deltas =
            ALIGN_GEOM::Deltas( boxes, aMode, targetBoxes[*target] );

    for( size_t i = 0; i < aItems.size(); ++i )
        moveItem( aItems[i].first, deltas[i], aCommit );
}
```

Then delete `selectTarget()` and its declaration once all six methods are converted — verify with
`grep -n selectTarget` that nothing still calls it.

Note this makes `SelectTargetIndex`'s "else the first" fallback carry the same meaning it had
before: `GetSelections()` sorts `aItems` by the edge being aligned, so `aItems.front()` is the
extreme item on that axis. `aLocked` is not sorted, so for locked items "first" means selection
order — which is also what the original did.

## Known limitations, deliberately not addressed

- **No distribute commands.** eeschema has none today (`sch_align_tool.h` declares only the six
  aligns), so adding them would be new functionality in two editors rather than parity work.
- **Container centring offers one container per editor.** pcbnew's own comment calls
  enclosing-item bounding boxes a follow-up; the same applies here. In the symbol editor that
  would mean centring inside *a* chosen rectangle rather than the whole body.
- **No preferences toggle**, consistent with the rest of the guide feature.
- **`SCH_ALIGN_TOOL` has no automated tests** before or after Task B1. The extraction is covered
  by `ALIGN_GEOM`'s unit tests; the tool's own wiring is not.
